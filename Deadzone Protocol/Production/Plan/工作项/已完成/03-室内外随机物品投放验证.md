状态：已完成，前置工作项 01、02 已完成。创建日期：2026-10-05；完成归档日期：2026-10-05。已完成室内外随机物品投放验证与离线 HTML 交付，结果及容量、性能限制见 [03-物品投放验证报告](../报告/03-物品投放验证报告.md)。下文保留原始执行要求，实际交付以报告为准。

## 1. 目标与前提

在已经验证的单层建筑、缓坡地形、玩家与敌人导航场景上，增加随机物品投放。暂不制作物品模型，用不同颜色的方块表示不同测试物品。必须能配置“哪些建筑/建筑区域生成哪些颜色”，并在区域内随机选择合法位置。

核心验收：方块确实出现在建筑室内可达的地板上；建筑旋转、抬高地坪、地形起伏和不同 seed 下仍合法；投放可以按区域控制颜色；不会堵住入口或破坏既有敌人通行。

这是一项空间投放验证，不实现正式 Inventory、掉落经济、装备、商店、稀有度或世界事件。颜色只是验证标签，不沿用游戏物品品质的颜色语义。

## 3. 运行场景与交付入口

交付本项 `Play.html`，可双击离线运行；内嵌所需脚本、WASM 与资源，不依赖服务器、外部请求或关闭安全策略。继承 02 的第一人称移动、真实敌人模型/动画、建筑与地形、导航和调试能力，不退回静态鸟瞰演示。

默认保留约 160 × 160 米、12～18 栋建筑、约 30 个敌人的验证规模，实际基线以 02 报告为准。物品初始目标约 80～120 个，每个场景至少有三个模板、多个建筑实例的室内投放和足量室外投放。数量配置化，不能为了凑数放入非法位置。

用边长约 0.25～0.4 米的方块作为物品，提供颜色与文本/调试标签对应表。方块可视且可定位；不要求物理动态掉落或拾取进背包。默认不作为阻挡角色的刚体，仍需遵守入口与通路禁放规则，避免视觉堆积。可以提供近距离选中/隐藏方块的调试操作，但这不是正式拾取功能。

## 4. 区域控制与配置要求

区域规则必须来自配置，不能散落在逻辑代码中。至少支持：

- 按建筑 templateId 选择规则；同模板多个随机实例都能应用。
- 按某个 building instanceId 覆盖规则，用于复现或定向测试。
- 按室内 regionId 或语义标签选择具体子区域。
- 区分室内、室外和禁放区域。
- 配置颜色/测试物品 ID、数量或数量范围、候选颜色权重、方块尺寸、最小间距。
- 对规则优先级和冲突有明确语义，例如实例覆盖模板；不允许靠遍历顺序偶然决定颜色。

至少交付这些可运行示例，模板 ID 映射到前序实际模板：

| 示例 | 预期 |
| --- | --- |
| 模板 A 的室内 | 只生成红色方块，位置在每个实例的合法室内区域中随机。 |
| 模板 B 的室内 | 只生成蓝色方块，不泄漏到建筑外包盒内但房间以外的位置。 |
| 模板 C 的两个室内子区域 | 两个区域分别指定绿色、黄色；必要时在本项为已有合法室内区域细分配置，不能改建筑模型伪造空间。 |
| 指定一个建筑实例 | 覆盖该实例为紫色，不改变同模板的其他实例。 |
| 室外区域 | 按配置生成白色或另一组独立颜色，不能落入室内或屋顶。 |
| 混合规则配置 | 单一区域按配置权重从两种颜色抽样，用于验证随机规则，不要求每次恰好达到比例。 |

至少有一组同时包含抬高地坪建筑、不同朝向建筑和相邻区域不同颜色的案例。可配置少量固定位置作为诊断参照，但主体必须是在区域内随机采样，不能把每栋建筑唯一固定点换个颜色称为随机分布。

## 5. 投放合法性

1. 先在目标建筑/区域的局部坐标中采样，再完整变换到世界坐标，或使用等价且经过验证的方法。旋转建筑时，区域和禁放范围必须一起旋转。
2. 方块底面落在目标支持面，中心高度考虑半高；室内使用实际室内地坪，室外使用真实地形高度。不能统一使用 y=0，也不能从天空向下取第一次命中而落在屋顶。
3. 检查方块完整体积，而非仅中心点：不穿墙、门框、地板和屋顶，不悬空、不在基础里、不与其他方块重叠；坡面放置要有明确朝向/支撑策略，必要时避开不适合放置的坡面。
4. 方块在声明的区域内，且处于玩家能从场景出生连通区到达并靠近的位置；验证访问位置而非只判断物品中心在导航面上。不能出现在狭缝、封闭角落、仅能从墙外看到的位置。
5. 门口、入口缓坡、主通道与转角保留净空，遵守前序禁放范围。必要时按方块半尺寸扩张障碍或收缩采样区域。
6. 初始生成避开玩家/敌人占用的体积，规定最小间距；运行中敌人走过非阻挡方块是允许行为，不需要动态追着敌人重放物品。
7. 搜索尝试次数有上限。请求数量超过容量时，返回实际数量、失败数量和原因，不无限循环、不把溢出方块投到区域外、不静默删除数量要求。
8. 固定 world seed、placement seed、配置和版本可以复现结果；物品使用独立随机流。只改物品配置或 placement seed 时，地形、建筑和敌人初始分布不应变化。

通过测试探明真实限制，不需要建立最终正式物品系统或通用配置编辑器。

## 6. 调试、测试与证据

页面显示世界 seed、物品 seed、颜色图例、按建筑/区域统计的请求数/成功数/失败数。提供区域边界、禁放范围、物品标识和位置的调试显示；能单独重新生成物品而保留世界布局。提供复制或导出分布清单的方式。

至少完成：

- 30 个固定 seed 的自动生成与合法性检查，覆盖数量、颜色约束、区域归属、体积重叠、支持面和可达性；保留 seed 清单与摘要。
- 三个代表性 seed 的实际浏览器检查：进入房间看方块、走上抬高地坪、检查转角和多个朝向建筑，验证室外方块随地形高度正确放置。
- 对同 seed 连续生成两次比较稳定清单；单改 placement seed 时物品变化，建筑/敌人初始布局签名不变。
- 对实例覆盖、模板规则、子区域规则分别检查，不能只看颜色大致分布。
- 请求超量、极小区域、零数量、未知模板/区域、非法权重等失败路径有明确可理解的处理；未知标识和非法配置应报错，零数量合法。
- 继承 02 的关键运动回归：玩家和至少 10 个敌人经过有物品的建筑入口/室内通路，不出现因投放导致的新阻塞。
- 重置场景、重新生成物品后无旧方块残留或资源持续增长。

自动检查应尽量使用碰撞/支持面/连通查询核验实际结果，而不是重复生成器的同一判断后直接宣布正确。浏览器截图至少包含全图分布、红/蓝两个建筑室内、不同子区域、抬高地坪和坡地室外物品。

记录测试机器、浏览器、分辨率、物品数和帧时间，与 02 同等配置比较新增开销，不承诺未实测的正式性能目标。file:// 未实际验证时明确列待人工验证，不能把 HTTP 测试当作双击入口通过。
